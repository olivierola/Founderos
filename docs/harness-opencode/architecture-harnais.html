01 · Architecture

Vue d'ensemble

Tout tourne dans un seul processus Node : la plateforme (base, authentification, stockage, temps réel), les fonctions edge portées depuis Supabase et, quand HARNESS_OPENCODE=1, le harnais OpenCode embarqué. Le front ne voit pas la différence : les deux moteurs écrivent dans les mêmes tables.

02 · Routage

L'aiguillage

L'aiguillage est monté juste devant les fonctions portées. Il lit le corps de la requête sans le consommer : s'il ne la prend pas, elle arrive intacte à l'ancien internal-agent-run. La bascule se fait agent par agent, par la colonne internal_agents.harness (migration 0307, en local seulement).

Quand l'aiguillage prend la requête, il fait les mêmes contrôles que l'ancien moteur avant d'engager la moindre dépense :

  • la clé de service, ou une personne qui a accès à l'agent ;
  • une conversation qui appartient bien à l'agent ;
  • des crédits et un quota suffisants pour l'espace.
03 · Séquence

Un tour de chat, de bout en bout

Le contrat avec le front est celui de l'ancien moteur. La personne a déjà enregistré son message, l'appel rend tout de suite un run_id, et la suite arrive par la base.

Avant la boucle (1 à 8)

  1. Le front enregistre le message dans internal_agent_messages, puis appelle la fonction.
  2. L'aiguillage vérifie l'accès, la conversation et les crédits (étape 3).
  3. Si un run est déjà en cours dans la conversation, le message entre dans sa session en steer : il est pris en compte à l'étape suivante, sans second run.
  4. Sinon le tour crée le run. Une conversation garde une session OpenCode ; la première fois, elle est amorcée avec les derniers échanges.
  5. Le profil de l'agent est relu (prompt, modèles). Le modèle du tour vient du composer, ou du classement de la demande (classifyRequest, AgentPilot, detectNeed). Un événement « status » le note dans la timeline.

Dans la boucle (9 à 15), puis la fin

  1. model.resolve donne le modèle du tour au travail de l'agent, et le palier léger aux titres et à la compaction.
  2. context ne laisse que le noyau et le lot ouvert, pose les vrais schémas et ajoute le contexte gardé.
  3. OpenCode exécute les appels d'outils ; l'outil regroupé appelle le handler de l'ancien moteur.
  4. Le pont transforme chaque événement en ligne de base, dans l'ordre, une file par session.
  5. À la fin, le pont écrit la réponse dans la conversation et clôt le run. Une annulation depuis le front interrompt la session.
04 · Configuration

L'instance d'un agent

L'hôte crée une instance OpenCode par agent FounderOS. La clé est l'agent_id porté par la session, et l'instance n'est construite qu'au premier message. Le plugin de l'agent la configure entièrement ; rien ne vient des fichiers de la machine.

fournisseur « founderos »

Connexion et modèles

Compatible OpenAI. La connexion est le connecteur de l'agent, son serveur GPU ou celle de la plateforme (OpenRouter par défaut). Un modèle par route (light, standard, heavy), avec ses replis OpenRouter.

agent « founderos »

Agent principal

Le prompt FounderOS remplace celui d'OpenCode : entreprise, self-model, et la section « Tes outils » qui décrit les lots. Limite d'étapes : max_steps × 15, de 60 à 400.

permissions

Ce qui est refusé

Tout est permis sauf shell et l'accès hors du dossier de l'agent : en local, ils toucheraient la machine qui héberge le backend.

hook model.resolve

Le modèle de chaque requête

Le travail prend le modèle choisi pour le tour ; un titre ou une compaction prend le palier léger.

hook context

Ce que voit le modèle

À chaque requête : retire les outils hors du noyau et du lot ouvert, pose les schémas JSON réels, ajoute <working_context>.

sous-agents et skills

Spécialistes

Cinq spécialistes déclarés en sous-agents. Les skills de l'agent sont embarqués et filtrés par permission. Les sous-agents livrés avec OpenCode sont retirés.

05 · Outillage

L'outillage par lots

Le modèle voit un noyau de huit outils et la liste des lots. Il ouvre le lot dont il a besoin et ne voit que ses outils. S'il s'est trompé, il en ouvre un autre, qui ferme le précédent. Chaque famille d'outils de l'ancien moteur est devenue un outil avec un paramètre action, dont chaque valeur est décrite.

07 · Délégation

Les spécialistes

L'agent principal reste le seul à parler à la personne, à décider et à tenir la mémoire. Une tâche bien délimitée part chez un spécialiste, dans une session enfant qui travaille en arrière-plan et ne voit que ce que la tâche demande.

08 · Persistance

Le pont d'événements

OpenCode publie des événements ; le pont les traduit en lignes que le front lit déjà. Chaque run est attaché à sa session, et les écritures d'une session passent dans l'ordre. Au redémarrage, les runs encore en cours sont rattachés : OpenCode reprend leur session et le pont reprend leur timeline.

09 · Filet de sécurité

L'ancien moteur

Il sert toujours les missions, les agents marqués legacy et tout le cloud Supabase. Ses handlers d'outils sont aussi ceux que le harnais OpenCode appelle derrière ses outils regroupés.

Ce que fait sa boucle

  • Streaming, avec outils lancés en parallèle par voies dès leur arrivée dans le flux.
  • Arrêt coopératif en 5 s, puis interruption.
  • Réparation des arguments, diagnostic des erreurs d'outil, nouvelles tentatives et délais.
  • Compaction hybride et sorties longues conservées à part.
  • Choix des outils par jugement rapide (Jev) et familles chargées à la demande.

Ce qui change avec OpenCode

  • OpenCode la boucle, le streaming, la compaction, les sous-agents, les questions, les permissions.
  • FounderOS le prompt, les modèles et paliers, l'outillage par lots, le contexte, les spécialistes, le pont.
  • ancien moteur les handlers d'outils, appelés tels quels, et les missions pour l'instant.

11 · Suite

Limites connues

  • Approbations. Les handlers tournent sans run : un outil qui demande une approbation humaine ne la demande pas encore sur ce chemin. Prévu en phase 4.
  • Historique du travail. Le type conversation de build_context dépend du run et ne rend rien pour l'instant.
  • État en mémoire. Le lot ouvert et le contexte gardé sont perdus au redémarrage du backend ; le modèle rouvre le lot.
  • Missions. Elles tournent encore sur l'ancien moteur ; seul le chat passe par OpenCode.
  • Exécution isolée. Le shell d'OpenCode reste refusé tant qu'il n'y a pas d'environnement isolé (phase 6) ; l'exécution passe par les machines distantes.
  • Réglages. La bascule d'un agent se fait en SQL, et le tri des skills entre spécialistes par mots-clés ; il manque les écrans correspondants.
  • Cache. Changer les outils d'une étape à l'autre casse le cache du bloc d'outils chez le fournisseur ; le prompt système reste en cache.
